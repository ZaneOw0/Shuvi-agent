## 结论

此前「长文档未完成」更准确的表述是：**一个有 232 个输入块的作业，在上轮我为安装修复版将应用切后台时，被暂停检查阻断；旧代码把准入写入后、实际发送前的阻断误记成 Unknown，随后按未知请求保护规则停止自动处理。没有证据表明它触发文档长度上限、模型 token 上限或服务限流。**

该作业的待嵌入正文/OCR 投影合计 16,352 个 Unicode 字符、21,088 个 UTF-8 字节。这个规模本身不算超长；232 块主要反映按结构块分别切分、短段未合并。块数不能当作页数、字数或 token 数。

当前实现有明确容量、时间及前台约束。它支持分块处理，但尚无足够实测证据承诺任意长文档都能在一次前台会话里完成。

## 当前代码中的边界

这些是仓库当前实现的本地约束，不是对云服务最新套餐或厂商最大容量的声明。

| 层次 | 当前边界 | 触发后表现/说明 |
|---|---|---|
| TXT / Markdown 正式入口 | 单文件 1 MiB；单批最多 10 文件、5 MiB | 文件预检拒绝，不会先全部发给模型 |
| PDF / DOCX 等解析原件 | 单文件 20 MiB | 解析入口体积约束；不等于可向量化字数 |
| PDF | 需能核定 1–50 原页 | 超页数/无法核定不能发起该解析流程 |
| 单个正文/OCR 输入块 | 最多 512 个 Unicode 码点、2,048 UTF-8 字节 | 按结构逐块切分；不会把整篇长文一次发给嵌入模型 |
| 单文档正文/OCR 块 | 最多 2,000 块 | 超出报 DocumentChunkBudget；不静默截断 |
| 单文档结构 | 最多 20,000 blocks、1,000 图片 occurrence | 结构复杂度也可能先于字数达到限制 |
| 全库当前输入预算 | 30,000 | 计入当前块、图片代理及未被统一路由替代的旧输入；不是只看可检索向量数量 |
| 本地受管派生空间 | 共享预算 500 MiB；单代快照 100 MiB | 多副本、历史/引用和向量元数据也占空间，不能将 500 MiB 视作纯正文容量 |
| 单次嵌入输入资格 | 固定 BAAI/bge-m3 本地工程基线，上界证明 ≤8,192 tokens | 每块及问题分别校验；证明失败不能靠截断或假计数放行 |
| 请求时限 | 每次最多 120 秒，并受队列剩余时间约束 | 网络响应未知不自动重发 |
| 自动处理轮次 | 每条 lane 15 分钟预算，作业取得剩余预算 | 并非每一块都有额外 15 分钟；长作业可能撞时间预算 |
| 并发 | 正文/图片代理共一条嵌入 lane；视觉独立一条 | 当前语料接口每次处理一个文本块，不是多块 batch 请求 |
| 后台与恢复 | 后台停止继续准入；真正 Unknown 保留待确认 | 修复后能够证明未调用 launch 的尝试记 NotSent，可暂停恢复；不翻写历史 Unknown |

**没有一个可对用户承诺的统一「最多多少字」数值。** 2,000 × 512 = 1,024,000 字符只是全部块都填满时的理论投影容量，不是产品已支持或已压测的一百万字。大量一两字短段、表格或列表也会消耗块预算；TXT 还受 1 MiB 文件大小约束，PDF 另受 50 页约束。实际可处理长度取这些条件的交集。

## 中断与恢复的具体含义

上轮出现的两个问题应区分：

1. 长正文仍运行时，新图被旧 Promise.all 调度器连带等待。该问题已改为独立 lane，并以受控回归证明长正文未结束时新图可完成；这解释图片为何等待，不是长正文失败原因。
2. 我为部署修复把应用切后台，旧代码在持久化 InFlight 后的发送检查抛 DispatchPaused，造成该正文作业停在 Unknown。最终代码已补 NotSent 边界回归，但旧账本保持原样，当前仍停在 120/232。没有对用户文档自动执行“接受可能重复费用并重试”。

如果随后通过正式作业入口明确重试，当前代码先核验已读回向量的输入 hash、配置绑定、维度和向量 hash，符合条件的 120 块可复用，继续剩余输入；这次只读报告没有实际执行恢复，因此不宣称剩余 112 块已完成。配置改变、向量损坏或来源换版可能使复用失效。

## 目前能与不能评价的性能

- 已验证：真实服务接收了 120 个块，120 条本机向量读回；不是文档超过模型单次上下文而整篇被拒绝。
- 已验证：短结构显著增加请求数；一次服务请求、计数、持久化和向量读回的固定开销会按块重复。
- 尚未测得：这份文档的纯处理总时长、平均每秒字符数、p50/p95 请求延迟、内存峰值、耗电、现金成本、真机及 2,000 块极限。当前账本没有足够完整的每请求起止时间；不能把包含 UI 操作、部署和等待的会话时间当吞吐基准。
- 尚未证明：长文档在频繁锁屏、退后台、断网和进程回收后的连续完成体验。已有受控回归不能替代这些真实耐久性验收。

后续工程优先项是：保留完整来源映射的短段合并、断点进度/失败原因的手机 UI、可核验的开始/结束时间和吞吐记录、单文档显式恢复入口。暂不据此扩大长度上限或改变批量请求契约；任何优化后仍需独立长文档实测。
