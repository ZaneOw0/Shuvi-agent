日期：2026-10-24。用户已批准“结果先保存，实际金额另行核账”的契约调整。底层接口、存储与恢复已实现；另已接入 debug 真实搜索，待设备验收。未自动获取账单，本轮开发测试没有新增真实收费调用。

debug 搜索使用独立加密执行库，用户提供币种 CNY，账户标签 `shuvi-dev-tavily`。授权卡披露本地 CNY 1.00 预留，不是报价、实际费用或收费上限。失败/取消也保留证据，重启不重放。原“最多一次持久化派发”已于 2026-10-30 取消，改为每次搜索单独确认、执行库按单行大小限流（约 30–60 次搜索记满后自动清空，见 §6.14），见 [spec 03 §6.12](../../../specs/03-联网搜索.md)；此前规则见 §6.11。账单导入仍未实现。下文“启动检查”指原有仅检查入口，不代表新增搜索装配。

## 1. 两种状态分别表示什么

| 操作状态 | 结果 | 预算与账单 |
|---|---|---|
| `IN_FLIGHT` | 调用正在进行，尚未保存结果 | 原预算预留仍占用 |
| `RESULT_RECORDED` | 成功结果已持久化，可交给后续处理 | `pendingInvoice` 存在，`invoice` 不存在；预留不释放 |
| `COMMITTED`，带 `invoice` | 原成功结果保持不变 | 有匹配的供应商逐请求账单证据，预算已结算 |
| `UNKNOWN_OUTCOME` | 无法确定是否执行成功 | 沿用原对账流程；不能当作“仅金额未知” |

`BudgetReservationSnapshot.actual` 沿用既有结构，在 `RESERVED` 状态包含初始化值，**不能用于展示实际扣费为零**。实际费用必须同时检查预算 `SETTLED` 和匹配的 `invoice`。供应商返回 `credits: 0` 也不会产生金额为零的账单。

搜索结果保存成功不等于后续模型回答成功。来源保存在操作记录中，后续任务状态变化不删除该记录。

## 2. 接口和调用顺序

1. `SearchUsageReceipts` 将已校验的工具响应绑定到完整 invocation、参数和结果摘要。
2. 应用层 `SearchPendingInvoice` 以宿主明确配置的非敏感账户标识和预算币种，生成 `PendingInvoice`。不得用 Key 充当账户标识，也不得凭空填币种或折算汇率。
3. 宿主显式注入 `RuntimeExecutionRecoveryBridgeConfig.pendingInvoice`。未注入或无法取得匹配记录时，原有缺失金额的拒绝行为保留；当前启动检查装配未注入该端口，真实任务继续禁用。
4. `RuntimeExecutionRecoveryBridge.recordOutcome` 在一个 durable CAS 事务中保存成功结果、待核账记录并释放执行租约。预算预留继续占用。只有事务成功，Runtime 才应用步骤结果。
5. 需要核账时，先停止并关闭 Runtime。可信宿主通过 `DurableExecutionRecoveryStore.openForInvoiceReconciliation` 打开独立会话，调用 `settleInvoice(invoice, actual, nowMs)`；完成后重新打开 Runtime 读取最新预算。

核账专用会话不能装配 `RuntimeExecutionRecoveryBridge`；普通运行会话的 `settleInvoice` 会拒绝。不同会话的写入仍由后端 CAS 防止丢失更新；CAS 失败必须重新打开并核对，不可盲目重试或重新调用搜索。

这不是模型或 MCP 可调用的核账工具。`VerifiedInvoice` 的“已核对”表示**宿主证据验证器的责任边界**，不是填入 `verifiedBy` 就能证明真实扣款。当前没有实现供应商账单下载器、管理页面或密码学账单验签。

## 3. 什么证据可以结算

`PendingInvoice` 包含 schema、供应商、账户范围、币种、服务端请求 ID、可用时的供应商请求 ID、known/unknown 用量与 credits、结果摘要；操作记录本身保存 task、step、operation、attempt、invocation、工具身份和参数摘要。不复制 API Key 或原始私密账单。

`VerifiedInvoice` 必须携带 operation、供应商、账户、币种、供应商请求 ID、结果摘要、账单和行号、账期、证据来源及 SHA-256 摘要、审核者和审核时间，以及安全整数表示的实际 `amountMicros`。

可信导入器必须在调用前核对供应商原始证据的真实性、逐请求粒度、请求关联、币种和精确金额，并提供实测的非货币 `BudgetAmount`。存储再次检查字段、关联和金额一致性；不会将 credits 或价格表转换成 actual。预留估价不限制真实账单入账金额，不能为了通过预算检查截断实际扣费。后续请求是否可执行另由预算与授权决定。

相同账单及相同实际用量重复提交返回 `UNCHANGED`；金额、摘要、币种、账户、请求或用量变化拒绝且不覆盖。一个供应商账单行不能分配给两个操作。冲突返回错误留待人工核查；本轮没有实现冲突处理页面或冲突历史表。退款、修订账单不能通过覆盖旧金额处理，需另行设计审计流程。

只有月度总额、缺少供应商请求 ID 或无法关联具体请求时，**不能调用逐请求结算接口**。调用记录保持待核账；账户/账期总额应由账务负责人单独核对，本轮尚未实现账期汇总账本或分摊功能。免费额度、套餐价格和余额变化不能替代逐次账单。

## 4. 失败、恢复和版本

- 写入失败不发布成功结果。可能已被供应商收费的调用不自动重发，保留执行未知的核对边界。
- 当前待核账路径只接受已校验的 `SUCCEEDED`。失败、拒绝、取消和执行未知不冒充成功，不自动填写零费用；其真实费用证据缺失时仍按原有保守路径拒绝或等待对账。失败响应账单导入是后续范围。
- 若进程在保存结果后、保存任务检查点前退出，恢复会使用已存成功结果完成该步骤，不再 dispatch。还有后续步骤时恢复为暂停，避免自动继续收费；全部步骤已完成则恢复完成状态。
- 存储 schema 从 `1.2` 升为 `1.3`。读旧快照时先验证摘要与全部结构，拒绝伪装为旧版的新字段；保留原结果、策略、预算和租约，递增 revision 并通过 CAS 保存。失败不清库、不重建“空数据”。
- 旧版应用不能读取 `1.3`，回退应用前需制定数据兼容方案；不要通过降低 schema 字符串强制降级。
- 记录继续使用现有加密 RDB 和快照机制。本轮没有新增自动清理；待核账义务不会因会话关闭而删除。正式发布前需团队确认账务记录保留周期与容量策略。
