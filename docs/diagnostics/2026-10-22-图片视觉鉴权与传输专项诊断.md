# 图片视觉鉴权与传输专项诊断

日期：2026-10-22。分支 `dev/rag`，诊断代码基线 `f1ebfed`。状态：只读诊断已完成；4 个视觉任务的底层传输原因尚未确认。本轮没有修改运行代码、修改设置、重新入队、发送图片、调用模型、清理资料或操作 Git 提交。

## 1. 用户问题与结论

用户在模拟器看到多条「图片描述与标签 · 结果待核对 · 0/1」，重试时出现 `ExplicitRetryAcceptsPossibleDuplicateCost`。本次核对实际持久化任务、尝试次数、设置/凭据版本，以及传输和调度代码。

**主要问题是旧凭据被多个不同图片任务使用后产生的一组鉴权失败，不能将其解释为大量断网。** 当前仍保留的 44 个 `Http:401` 任务全部绑定旧凭据版本 1；当前凭据版本为 2。另有 4 个任务在版本 2 下为 `NetworkOrCanceledUnknown`，与旧 401 是不同问题。版本 2 已有 16 个视觉任务和 16 个图片描述向量任务完成。

401 的意思是服务没有认可请求携带的 API 身份凭据。DeepSeek 官方将其定义为 API Key 鉴权失败；余额不足为 402，频率/并发限制为 429，服务过载为 503。不能将 401 推断成断网、余额不足或数据库写入失败。参考 [DeepSeek 错误码](https://api-docs.deepseek.com/quick_start/error_codes/)。本次不读取 Key，不能进一步判定旧 Key 是填错、失效还是来源不匹配。

当前视觉设置为 revision=4、credentialRevision=2，enabled/automatic=true、paused=false。版本 4 的视觉尝试共有 16 次 Received、8 次 Unknown，后者属于上述 4 个尚未完成任务。这些次数含重试，不是独立样本成功率，也不能称为纯网络故障率。

**44 条 401 是 44 个不同任务各失败一次，不是某张图片被自动无限重试 44 次。** 这 44 条均未切换到新凭据版本重新执行。更新 Key 不会自动改写历史结果，历史 Unknown 也不会被自动重发，故页面可长期保留大量旧警告。

## 3. 为什么一次凭据问题会产生这么多警告

代码路径 `UnifiedProcessingQueue.enqueue → lane → ImageKnowledgeService.process → VisionTransportAdapter.describe → VisionCredentialStore.fetch`：

1. 导入一份含多图资料时，每个图片 occurrence 生成一个独立 Vision 任务。描述缓存只在成功后可供后续复用。
2. 视觉 lane 串行处理图片，嵌入另有一个 lane；没有应用层同时发送几十个视觉请求的实现。
3. 当前缺少「某凭据版本第一次 401 后停止同版本后续视觉请求」的机制。单个任务失败后，循环会继续取下一张图，因此一份 42 张图的资料可积累 42 个鉴权失败。
4. 当前源码已将新收到的 auth 类失败设为 Failed；这 44 条保留为 Unknown 是旧状态记录，代码不会在启动时把它们改写成当前状态。仅显示 Unknown 会掩盖明确的鉴权拒绝。
5. 凭据发送代码使用固定 DeepSeek 地址和 Bearer 头，图片理解凭据使用独立安全存储 alias。源码未发现把 MinerU Token 或嵌入凭据直接拿来发视觉请求的路径；本结论不等于检查过 Key 的实际内容。

因此，主要改进方向是同凭据版本的鉴权失败阻断及历史状态的正确展示，而不是靠加大网络重试次数解决 401。

## 4. 4 个不确定任务的针对排查

### 已确认的差异

| 结果 | 图片文件大小 | 像素情况 |
| --- | --- | --- |
| 16 个成功任务 | 4,766–82,046 字节 | 最大为 1600 × 800，128 万像素 |
| 不确定任务 A | 1,043,975 字节，PNG | 1376 × 1753，约 241 万像素 |
| 不确定任务 B | 223,458 字节，JPEG | 1249 × 1837，约 229 万像素 |
| 不确定任务 C | 317,735 字节，JPEG | 1280 × 2774，约 355 万像素 |
| 不确定任务 D | 299,461 字节，JPEG | 1348 × 1724，约 232 万像素 |

传输使用原始图片 Base64，`detail=original`，没有缩图。4 张图均在应用的 20 MiB / 2000 万像素上限以内，其体积也低于官方 inline 单图 32 MiB 限制；不能把当前错误解释为已经确认超出图片体积上限。官方说明 original 保留原图，low 会缩至 512 × 512；参考 [DeepSeek 图像理解](https://api-docs.deepseek.com/guides/vision/)。本轮未更改分辨率策略。

### 超时与错误归类问题

`VisionTransportAdapter` 设置连接 30 秒、无数据活动 30 秒、传输 120 秒，并有最长 120 秒的应用计时器。队列另有每轮 15 分钟期限；接近该期限时应用计时器可能短于 120 秒。

官方 RCP 文档说明 `inactivityMs` 限制没有数据传输/连接活动的最长间隔。因此，**即使总传输时限为 120 秒，等待模型返回时连续 30 秒无活动也可能先触发 SDK 超时**。官方 DeepSeek 还说明非流式请求可能等待并以空行保活；不能据此保证任意请求在 30 秒内必定出现活动。参考 [DeepSeek 等待与保活](https://api-docs.deepseek.com/quick_start/rate_limit/)。

较大的原图与更短的无活动时限，构成值得优先复现的超时线索；没有耗时和 SDK 错误码，**尚不能证明这 4 个任务就是 30 秒超时，更不能直接归因于模拟器 DNS、代理、证书或供应商故障**。

当前 catch 把所有非 `VisionFailure` 异常在已 launch 时统一覆盖为 `NetworkOrCanceledUnknown`。其中可能包含 SDK 超时、解析域名/连接/TLS 错误、连接中断、取消，以及请求过程中的其他异常。原始 BusinessError 数字码、发生阶段、耗时与取消来源没有持久化。`launched=true` 也只证明调用过 `session.fetch`，不证明服务已完整收到图片或已处理。

应用退后台会阻止队列发起下一任务；不能把普通切页直接等同于主动取消当前视觉请求。显式暂停/停止会使 cancellation 失效，进程退出也可能导致结果无法确认。没有对应事件时间，无法将这类行为和 4 个未知结果逐一关联。

### 现有证据的边界

- 任务与尝试模型均没有开始/完成时间字段；实际查询也没有发现相应时间字段。只能按配置版本区分，无法还原每次请求的准确时序。
- 用 CLI 对现有应用 E 级日志进行最近 1440 分钟、最多 20000 行的本地类别统计，没有取得可关联到这些任务的 RCP/DNS/TLS/超时错误。没有输出原始日志；「没有取得」不等于「没有发生」。
- 查询时 [DeepSeek 状态页](https://status.deepseek.com/) 显示整体正常。这仅是查询时的全局状态，不能证明过去某次请求或本机链路正常。
- 本轮没有再次调用模型，没有做模拟器 DNS/TLS 探针或断网注入，也没有实际验证放宽超时/缩图后的改善。

## 5. 页面提示缺陷

`retryUnknown` 把 `ExplicitRetryAcceptsPossibleDuplicateCost` 写入 failure 字段，含义为用户接受重试可能重复计费。重新进入 Pending/Running 时该字段未清空，页面又对任何非空 failure 渲染失败文案，形成「处理中，却显示未完成原因为内部授权标记」的矛盾提示。

该标记不是服务错误、不是数据库错误，也不是已重复扣费的证据。当前图片任务真实完成后 failure 会清空，但进行中展示已经会误导。本轮仅确认根因，未修改实现。

## 6. 后续修复优先级

1. **鉴权失败阻断**：首次 401 后停止同凭据版本的后续视觉派发；其余任务显示等待更新图片理解凭据，正文与已完成结果保留。更新凭据后仍不擅自重发历史未知任务；403 应按实际权限拒绝处理，不能无限重试。
2. **明确结果状态**：旧 `Http:401` 在展示层明确为鉴权失败；重试授权标记不再作为 failure 文案，排队/处理中显示真实阶段。
3. **补足安全诊断数据**：记录尝试起止时间、阶段、耗时、白名单 SDK 数字错误码、HTTP 状态、图片字节/尺寸与取消原因。禁止记录 Key、Authorization、原图 Base64、请求/响应正文或 SDK 原始异常文本。
4. **受控验证超时假设**：在诊断能力就绪后，用自制不同尺寸图片、相同模型与参数逐项对照；核对连接/等待响应/总传输的实际耗时，再决定是否调整无活动时限或图片策略。不能直接以多次重试用户图片代替诊断。

以上是本轮诊断建议，不表示相应代码修复或真实服务复验已经完成。
