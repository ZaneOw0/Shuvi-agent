# 03 鸿蒙核心概念速览

> 状态：参考文档。汇总 HAP、Stage 模型及相关工程概念，供团队对齐术语；随平台基线变化更新。
> 通用概念依据本机 HarmonyOS 26.0.0 配套开发文档整理；仓库现状对照以 `dev/platform` 分支为准。
> 项目目标见 [00-项目总览](00-项目总览.md)，协作规则见 [01-协作与工程约定](01-协作与工程约定.md)，平台基线见 [02-平台基线](02-平台基线.md)。

## 一、HAP 是什么

**HAP（Harmony Ability Package）是鸿蒙应用「安装和运行」的基本单元**，由代码、资源、第三方库、配置文件打包而成。

- 应用可以只包含一个基础 **entry** 包，也可以由一个 entry 包 + 多个 **feature** 包组成。
- 设备上真正被安装、启动的是 HAP，而不是 App 包。
- debug 调试时产物为 `.hap` 文件，可通过 DevEco Studio 或命令行直接安装到设备。

## 二、包类型全景：App / HAP / HAR / HSP

| 概念 | 全称 / 定位 | 能否独立安装 | 共享范围 | 资源复用方式 |
|---|---|---|---|---|
| **App** | 发布到应用市场的基本单元（`.app`） | 否，需上架分发 | — | 包含一个或多个 HAP / HSP |
| **HAP** | Harmony Ability Package，安装与运行的基本单元 | 是（调试直装） | 不可跨应用共享 | 不涉及 |
| **HAR** | Harmony Archive，静态共享包 | 否，编译时被打进引用方 | 应用内；可发布 OHPM 中心仓/私仓 | 编译时**复制**到引用模块 |
| **HSP** | Harmony Shared Package，动态共享包 | 否，随宿主 App 一起发布 | 仅应用内（与宿主同包名、同进程、同生命周期） | 运行时**动态加载**，只保留一份 |

关键差异：

- **HAR 会被拷贝多份**：多个 HAP/HSP 引用同一个 HAR 时，各自拷贝一份，会撑大包体；重复的大资源（图片、视频）建议改用 HSP。
- **HSP 不能独立上架**，也不能作为共享包给其他应用使用；HAR 才可以发布到 OHPM 供他方使用。
- **HAR 不能声明 UIAbility / AbilityStage**：`AbilityStage` 与 HAP 一一对应；HAR 也不宜依赖 `AppScope` 资源。

## 三、Module：Ability 与 Library

同一个应用包含一个或多个 Module，Module 分两类：

| Module 类型 | 编译产物 | 说明 |
|---|---|---|
| **Ability 类型** | **HAP** | 承载应用组件（Ability）与页面 |
| **Library 类型** | **HAR 或 HSP** | 只做代码/资源复用，不承载独立入口 |

HAP 又分两种：

| HAP 类型 | 数量限制 | 用途 |
|---|---|---|
| **entry** | 同一设备类型**有且仅有一个** | 应用入口模块：启动页、入口图标、主特性，程序启动加载的就是它 |
| **feature** | 0 ~ n 个 | 动态特性模块，可配置为按需下载，或随 entry 一起下载 |

> 程序启动入口只能是 entry 类型，不能指定加载某个 feature；但模块的 `type` 可以在 entry / feature 之间修改，只要保证只有一个 entry。

## 四、Stage 模型

**Stage 模型**是 API 9 起支持、当前主推且长期演进的应用模型。它提供了两个“舞台”，故得名 Stage：

- **AbilityStage**：应用组件的舞台（组件管理器）
- **WindowStage**：窗口的舞台（窗口管理器）

### 4.1 核心概念

| 概念 | 说明 |
|---|---|
| **AbilityStage** | 每个 entry / feature 类型的 HAP 在运行期都有一个实例；HAP 代码首次被加载进进程时创建，可做初始化 |
| **UIAbility** | 包含 UI 的应用组件，负责与用户交互；一个 HAP 可含一个或多个 UIAbility，运行时共用同一 AbilityStage |
| **ExtensionAbility** | 面向特定场景的应用组件，不直接派生，而是使用派生子类（如卡片 `FormExtensionAbility`、输入法 `InputMethodExtensionAbility`、延时任务 `WorkSchedulerExtensionAbility`）。三方应用不能自定义服务，需按场景选派生类 |
| **WindowStage** | 每个 UIAbility 实例绑定一个；内含一个主窗口，为 ArkUI 提供绘制区域，可加载不同页面 |
| **Context** | 运行期访问资源与能力的入口；不同组件有各自的 Context 子类，均继承自基类 Context |
| **ArkUI 页面** | 基于 ArkUI 的用户界面，UIAbility 通过它展示功能并与用户交互 |
| **Application** | 应用在设备上的运行实例，由一个或多个 HAP 构成，可共享一个或多个 HSP 的代码与资源 |
| **Bundle** | 安装部署阶段的静态文件集合（所有 HAP、HSP 及资源），安装启动后形成运行期实例 Application |

### 4.2 与 FA 模型的关系

- **FA 模型**：API 7 起支持，已不再主推，当前主要用于 Lite Wearable。
- **Stage 模型**：API 9 起支持，文档中未特别说明时，“应用模型”默认指 Stage 模型。

### 4.3 应用启动链路

1. 系统孵化进程并拉起应用主进程，创建运行环境
2. 加载**入口模块（entry HAP）**，创建 AbilityStage 实例
3. 启动入口 UIAbility
4. 创建 WindowStage 实例并与之绑定
5. 通过 WindowStage 加载首个 ArkUI 页面并呈现

### 4.4 UIAbility 生命周期

核心回调顺序：

```
onCreate → onWindowStageCreate → onForeground → onBackground → onWindowStageDestroy → onDestroy
```

- 核心四态：`onCreate`、`onForeground`、`onBackground`、`onDestroy`
- 与窗口相关的状态通过 **WindowStage 事件**暴露
- **必须在 `onWindowStageCreate` 中指定加载页面**（`windowStage.loadContent('pages/Index')`），否则启动后白屏

## 五、工程配置与文件对应

| 文件 | 层级 | 关键内容 |
|---|---|---|
| `AppScope/app.json5` | 应用级 | `bundleName`、`versionCode`、`versionName`、`icon`、`label` |
| `entry/src/main/module.json5` | 模块级 | `name`、`type`（entry/feature/shared）、`mainElement`、`deviceTypes`、`pages`、`abilities`、`requestPermissions` |
| 根 `build-profile.json5` | 工程级 | `products`、`signingConfigs`、`buildModeSet`、`modules` 注册 |
| 模块 `build-profile.json5` | 模块级 | `apiType: stageMode`、`targets`（default / ohosTest） |
| `oh-package.json5` | 工程/模块级 | 依赖声明（OHPM） |
| `hvigorfile.ts` | 构建 | 根工程用 `appTasks`；HAP 用 `hapTasks`；HAR 用 `harTasks`；HSP 用 `hspTasks` |
| `resources/base\|dark/...` | 资源 | `element`（字符串/颜色/浮点）、`media`、`profile` |
| `resources/base/profile/main_pages.json` | 路由 | 页面清单，必须与 `EntryAbility` 的 `loadContent` 一致 |

## 六、常见误区速查

| 误区 | 正解 |
|---|---|
| App 包能直接安装 | 不能；App 包需经应用市场分发，最终安装的是其中的 HAP |
| 一个应用可以有好几个 entry | 同一设备类型只允许一个 entry 类型 HAP |
| HAP 可以给别的应用复用 | 不能；跨应用共享用 HAR，应用内共享用 HSP |
| HAR 和 HSP 差不多 | 复用方式不同：HAR 编译期拷贝（易膨胀），HSP 运行期共享（省空间） |
| HAR 里可以声明 Ability | 不能；`AbilityStage` 与 HAP 一一对应，Ability 需在 HAP 的 `module.json5` 中声明 |
| HSP 能独立上架 | 不能；HSP 跟随宿主 App 发布，同进程、同包名、同生命周期 |

## 七、本仓现状对照（Shuvi）

> 现状基于 `dev/platform` 分支最新提交。

| 概念 | 当前状态 |
|---|---|
| **entry HAP** | 已建立：`entry/`（Stage 模型，`type: entry`，`deviceTypes: phone`；零权限、无业务逻辑） |
| **应用级配置** | `AppScope/app.json5`；`bundleName` 暂用占位 `com.example.shuvi` |
| **模块注册** | 根 `build-profile.json5` 的 `modules` 已注册 `entry`（`srcPath: ./entry`，target `default`） |
| **Library 类型模块** | 规划的 `assistant_core`、`platform_adapter` 对应 HAR（尚未创建） |
| **签名配置** | 入库模板不含 `signingConfigs`；签名材料由各成员本机生成（`~/.ohos/config`），不入库 |
| **构建产物** | `.hap` 位于 `entry/build/.../outputs`（已忽略，不入库） |
| **本地一键脚本** | `scripts/dev-run.sh`（Bash）与 `scripts/dev-run.cmd`（Windows 包装），串联：设备/模拟器 → 签名 → 构建 → 安装运行 |
| **脚本选项** | `--emulator <name>`、`--device <serial>`、`--product <name>`、`--force-sign`、`--no-build`、`--no-emulator`；环境变量 `EMULATOR_NAME`、`PRODUCT` |
| **行尾约定** | `.gitattributes`：`*.sh` 用 LF，`*.cmd` / `*.bat` 用 CRLF |
| **契约骨架** | `specs/README.md` 与 `specs/_模板.md` 已建立，尚无具体功能 spec |

**一键脚本流程（`scripts/dev-run.sh`）**

1. **设备**：有活动设备直接用；否则自动选/启动模拟器，并等待设备就绪（最多 240 秒）
2. **签名**：本机无签名配置时自动 `devecocli signature generate`（需先 `devecocli auth login`）
3. **构建**：`devecocli build`（可用 `--no-build` 跳过）
4. **安装运行**：`devecocli run --skip-build`，失败自动重试 3 次

> Windows 下执行 `scripts\dev-run.cmd`，其余与 Bash 版一致；脚本行尾由 `.gitattributes` 固定，避免 Windows 检出把 `.sh` 改成 CRLF 导致无法执行。
