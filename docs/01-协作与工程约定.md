# 01 协作与工程约定

> 面向 DevEco Code 辅助开发。目标是以少量、可执行的规则保持快速迭代、稳定集成和可复现交付。项目目标见 [00-项目总览](00-项目总览.md)，平台基线见 [02-平台基线](02-平台基线.md)。

## 1. 分工与协作

| 主责 | 工作范围 | 负责人 | 开发分支 |
|---|---|---|---|
| 产品与应用体验 | 用户流程、ArkUI、页面状态、交互与演示 | 待定 | `dev/ux` |
| Agent 与业务核心 | 主控、子智能体、契约、规则、提示词与评测 | 待定 | `dev/agent` |
| 平台与工程集成 | 提醒、权限、存储、网络、构建与真机验证 | 待定 | `dev/platform` |

### 1.1 分支规划
`main` 之下按三个主责设立长期开发分支，与 [00-项目总览](00-项目总览.md) 第 3 节的模块划分对应：

| 分支 | 主责 | 主要落点模块 |
|---|---|---|
| `dev/ux` | 产品与应用体验 | entry：页面、交互、路由 |
| `dev/agent` | Agent 与业务核心 | assistant_core：编排、契约、规则 |
| `dev/platform` | 平台与工程集成 | platform_adapter 与工程配置、CI、签名 |

功能级短分支从对应 `dev/*` 分支切出；`dev/*` 分支定期同步合并回 `main`，合并与评审规则沿用第 3 节 Git 管理。三条 `dev/*` 长分支在各主责线实际开工时从 `main` 切出，不在基线阶段预建。

### 1.2 开工顺序与时间线

1. 基线准备（main）：Git 初始化、补齐 [02-平台基线](02-平台基线.md) 待确认项、搭建 `specs/` 契约骨架。
2. 平台开工（从 `main` 切出 `dev/platform`）：先跑通构建、签名安装与真机运行最小 entry，再对提醒、模型接入做平台能力探针；另两条线的可验证性依赖该环境，故最先启动。
3. 并行开工（从 `main` 分别切出 `dev/ux` 与 `dev/agent`）：体验线以固定样例数据先做页面闭环；核心线契约先行，先定接口、工具与提示词初版，配合假适配器与确定性规则；双方以 `specs/` 契约为唯一对齐点。
4. 契约联调：由平台线提供真实适配器替换假适配器，页面逻辑不动，走通第一个最小用户闭环（如创建日程并提醒）。
5. 迭代集成：按用户闭环逐个实现，每完成一个闭环合并回 `main` 并补充评测。
6. 冻结发布：功能冻结、整理发布记录并打 tag。

## 2. 功能 spec 与开发流程

开发单位是用户闭环，每项功能按以下顺序描述：

**用户流程 → 页面事项 → 业务与 Agent 事项 → 平台能力 → 验收方式。**

最小 spec 包含：

- 目标、优先级、负责人、范围与非目标；
- 输入输出、数据归属、权限，以及超时、取消、重试、幂等与部分失败处理；
- 验收案例按 [00-项目总览](00-项目总览.md) 的四类路径覆盖：正常、异常、权限拒绝、模型失败。

跨模块契约先形成共同理解，再并行实现。页面可以使用固定样例，核心可以使用假适配器，但 Mock 结果不能作为真实链路完成证据。

日常流程：Issue/任务卡 → 简短 spec → 功能分支 → 实现与验证 → PR/MR → 评审合并 → 真机集成。文案等小改动不强制新增完整 spec。

## 3. Git 管理


- 托管平台遵守赛事要求，选一个权威仓库，避免多个平台分别开发。
- `main` 保持可集成、可演示；禁止直接推送与 force push。
- 使用至少3个分支分别维护三个主责模块开发，定期同步 merge 到 main。
- 一个分支处理一个目标，尽量在一至三天内合并；大功能拆成兼容的小步。
- 提交格式：`类型(范围): 中文描述`，如 `feat(calendar): 增加日程确认卡片`。
- 
- 提交类型汇总：

| 类型 | 说明 | 示例 |
|---|---|---|
| feat | 新增功能或能力 | `feat(calendar): 增加日程确认卡片` |
| fix | 修复缺陷或异常行为 | `fix(agent): 修复提醒重复触发问题` |
| docs | 仅文档变更，不影响代码 | `docs: 补充平台基线版本说明` |
| style | 代码格式调整，不改变逻辑 | `style(ui): 统一缩进与命名格式` |
| refactor | 重构，既非新增功能也非修复缺陷 | `refactor(storage): 抽取公共持久化封装` |
| perf | 性能优化 | `perf(list): 优化日程列表渲染性能` |
| test | 新增或修改测试与评测 | `test(time): 补充时间规则边界用例` |
| build | 构建系统或依赖变更 | `build: 升级 OHPM 依赖版本` |
| ci | CI/CD 流水线配置变更 | `ci: 增加 ArkTS 检查门禁` |
| chore | 杂项维护，不影响源码与测试 | `chore: 更新 .gitignore` |
| revert | 回滚已有提交 | `revert: 回滚 feat(calendar) 提交` |

- 单个提交聚焦一个逻辑变化，不混入无关格式化或依赖升级。
- PR/MR 至少由另一名成员评审，建议 squash merge；作者处理反馈并对结果负责。
- 公共契约、SDK、权限、存储结构和模型服务变化须由相关负责人共同评审。
- 冲突由改动相关人员处理并复验，不直接选取一侧覆盖。
- 每人使用独立本地克隆；并行 AI 任务按需隔离工作目录，不共同修改同一份未提交文件。

里程碑在已验收提交上打 tag，关联制品与验收记录。提交比赛前冻结功能；紧急修复也须回到主干并补齐记录。

## 4. ArkTS 与工程边界

- SDK、工具链与依赖基线以 [02-平台基线](02-平台基线.md) 为准，升级单独评审；依赖通过 OHPM 管理，提交工具生成的锁文件，不随意重建或手改。
- ArkTS 不等同于任意 TypeScript/Node.js 环境；第三方库必须验证目标 SDK、运行能力和许可证。
- 对外接口使用明确类型；模型与网络数据必须运行时校验，类型断言不能替代验证。
- 模块组织与依赖方向见 [00-项目总览](00-项目总览.md) 第 3 节；公共层只沉淀已稳定复用的机制，禁止成为杂物目录。
- 长耗时调用异步执行，避免阻塞 UI；页面离开、用户取消和进程终止分别定义行为。
- 持久化结构有版本和升级策略；涉及系统写入的操作具有稳定标识和结果记录；系统错误转为可理解提示，同时保留定位信息。

## 5. 模型、权限与个人数据

- 模型服务经统一接口接入，集中管理超时、取消、有限重试、错误与用量；契约版本化与效果评测要求见第 7 节。
- 工具执行校验参数、当前权限和用户意图；涉及日程等实际变更提供确认及结果反馈。
- 图片、语音、日程和对话遵循最小必要使用原则，明确外发服务、用途与保存方式。
- 不将团队共享 API Key 内置于公开安装包；用户自配密钥或受控转发方案另行决策。
- 配置模板可提交；密钥、私有配置、签名证书及密码不得进入 Git、截图、日志或 AI 上下文。疑似泄漏立即轮换密钥，并在团队内记录处置过程。
- 不随意清除本机日历、个人数据或测试设备的既有内容。测试优先使用专用账户及可识别的样例记录。

## 6. DevEco Code 使用约定

团队工程规则集中维护于仓库文档，由 DevEco Code 通过仓库上下文读取，不依赖特定文件名。交给 AI 的任务说明包含目标、spec、SDK/API、允许修改范围、约束和验收方式。

- 先阅读相关规范与现有接口，再修改。
- 不编造系统 API；新增能力说明官方依据、版本和权限条件。
- 不擅自新增依赖、权限、云服务或改变公共契约。
- 不用未经验证的兜底数据伪装成功，不为通过测试而削弱业务约束。
- 写入、命令执行和外部操作遵守当前任务授权；用户要求审批时，先展示具体方案并等待批准。
- AI 交付附验证说明，字段要求见第 9 节 PR/MR 说明；不得声称未执行的测试通过。

人类作者必须能解释 AI 生成的改动。AI 自评不能代替另一名成员的 PR 评审；对话中的正式决策需要回写仓库文档。

## 7. 测试、评测与 CI

以目标版本的 Test Kit、Hypium 和 UI 测试能力为基础，分层验证：

| 层次 | 重点 |
|---|---|
| 确定性测试 | 时间规则、参数校验、状态转换、权限结果、幂等与错误处理 |
| Agent 效果评测 | 固定输入、期望字段、澄清行为、工具选择、失败样例 |
| 平台集成 | 日历、通知、权限、模型网络、持久化与恢复 |
| 真机端到端 | 输入至提醒完整流程、后台、重启、重复操作、拒绝授权 |

评测记录可复现所需的关键信息：数据集、代码提交、模型与提示词版本、参数、运行环境和结果。生成式输出允许波动，但字段、业务规则和副作用必须满足明确约束。

PR 门禁以 ArkTS 检查、Hvigor 构建及相关确定性测试为合并必要条件；模型相关改动补充效果评测；普通文档修改不要求构建，影响系统能力的改动不能仅凭预览器或编译通过验收。CI 的 SDK、依赖和签名来源必须可复现。设备测试无法自动执行时，明确人工门禁，不冒充已自动覆盖。

### 7.1 已落地的 CI 门禁

配置见 `.github/workflows/ci.yml`，执行逻辑见 `scripts/ci-windows.cmd`。

- **触发**：`pull_request → main`（合并前门禁）与 `push → main`（合并后复核）；其他分支不触发。
- **执行**：自托管 runner（标签 `self-hosted`、`harmonyos`），顺序为依赖安装 → 代码检查 → 构建。
- **强制**：`main` 受保护，合并前须通过该检查并获得 1 个批准。
- **隔离**：fork 的 PR 由 job 条件跳过，不在自托管 runner 上执行外部代码。
- **已知限制**：`codelinter` 退出码恒为 1，不能作判定依据，门禁改用其 JSON 报告；ArkTS 严格规则由构建阶段的 `CompileArkTS` 拦截；CI 不签名、不安装、不做设备测试，真机验收仍为人工门禁。
- **可用性前提**：runner 未安装为系统服务，离线时任务排队，相关 PR 因必需检查未通过而无法合并。

## 8. 文档与变更记录

- 00 定义项目目标与架构基线，01 定义协作规则，02 统一记录平台配置与工具版本；功能字段与行为集中在对应 spec，不多处重复定义。
- 文档使用中文，技术名词保留原文；中英文间留空格，命名统一。
- 每份 spec 与关键文档头部带状态字段，按「待确认、已确认待实现、已实现待验收、已验收、已下线」流转；状态变化附版本与证据，格式参考 [00-项目总览](00-项目总览.md) 头部状态行。
- 改变接口、权限、行为或配置时，在同一个 PR 中更新相关文档。
- 重要决策记录背景、选择、理由、代价和适用范围；私人草稿不能成为团队唯一依据。
- 旧设计归档并注明替代文档；功能下线同步更新总览、入口、契约和验收。
- 失败样例和缺陷记录保留输入、预期、实际、复现条件及处理结果。

## 9. 完成与发布标准

PR/MR 说明至少包含：解决的问题、改动范围、契约/权限/数据影响、验证结果、未覆盖项与恢复办法。

功能完成须满足：

1. 约定用户闭环可操作，异常和权限路径有明确结果。
2. 契约、实现、页面与文档一致，相关测试和评测通过。
3. 无泄漏密钥、无关改动或未说明的新依赖。
4. 已知限制透明，评审反馈已处理。

发布须有发布记录并打 tag：记录提交 SHA/tag、制品与验收结果；SDK 与设备基线、签名方式、模型配置标识等按 [02-平台基线](02-平台基线.md) 记录。保留上一版本；涉及存储升级时说明数据恢复与兼容策略，不能只更换安装包。
