# ADR-016：T53 协作策略的异步准备与同步选择

状态：Accepted。项目所有者已在本轮对话明确同意；2026-10-19 完成实现与本地主机验证，代码待人工审核。

日期：2026-10-19。

基线：`codex/module-masrouter-t52` / `75590eb`，包含本地 T52 审核修复。T52 修复尚未提交；本 ADR 不将 T53 标记为完成。

## 1. 问题与依据

`RuntimePorts.ets` 中 `CollaborationPlanSelectorPort.selectPlan(frame, maxAgentActivations)` 同步返回 `CollaborationPlan`；`RuntimeCoordinator.beginPlanning()` 在调用 Planner 之前执行它。

M11 的 `ArtifactPolicyReleaseRunner.run(request, cancellation)` 返回 Promise，其超时、取消、shadow/canary/active 回退也依赖异步调用。不能用类型断言把 Promise 当作计划，不能在同步 selector 中等待网络或 embedding，也不能另写一套同步发布系统规避 M11。

任务书明确要求：如需异步 feature preparation，先形成兼容 Planner/FIFO/timeout/cancel 的 ADR，验收后再实现。本方案把未来特征准备与当前策略加载/评估归入同一个有界准备阶段；T53 不执行任何真实网络或特征服务。

## 2. 建议决策

保留现有同步 `CollaborationPlanSelectorPort` 和所有 `AgentRuntimeFacade` 方法签名。新增可选的组合端口 `CollaborationPolicyPreparationPort`，由 Runtime 在已有异步规划流程内部等待；原有同步 selector 只消费经过准备、验证且与当前任务绑定的本地候选。

拟议端口职责（具体 DTO 在实现时与现有类型对齐）：

```text
prepare(frame, executionBudget, cancellation) -> Promise<PreparedCollaborationDecision>
```

结果包含版本、taskId、输入/Registry/策略摘要、决策或稳定失败原因；不包含凭据、任务控制命令或授权 grant。适配器及 loader 不能提交或推进任务。

`ProductionAgentRuntimePorts` 增加可选准备端口，composition version 从 2.5 升至 2.6；默认不注入，既有调用方走原路径。不能同时注入两套互不绑定的准备器和 selector；由专用组合工厂返回绑定的一对组件。MCP/Provider/RDB 组合路径必须透传同一组端口，遗漏时拒绝配置，不能静默退回另一套策略。

## 3. 准备与选择流程

1. Runtime 生成 TaskFrame，复制预算和当前 Role/Model Registry 快照。
2. 同步计算并验证 Single baseline。baseline 自身无效时终止规划，不伪造成功。
3. `learnedEnabled=false` 为默认；关闭时不调用 loader、研究产物或外部服务，直接沿 baseline。
4. 显式启用测试配置时，loader 只装载 fake/research-only 候选，通过既有 M11 release runner 执行有界评估。研究 fixture 不进入真实生产 active Registry；测试用 release view 必须明确标记为 fake。
5. 校验所有输出：结构/版本、有限数值、置信度、角色顺序与去重、Role identity/digest、候选模型身份、输入摘要及 activation budget。模型只作为建议，不能授予调用权限。
6. 将合法候选转换成现有 CollaborationPlan，经过 CollaborationPlanValidator；同步 selectPlan 再检查任务、快照及预算绑定，返回防御性副本。
7. Runtime 先登记完整 activation 占用，再调用 Planner；不增加第二份互不一致的预算账本。明确区分当前计划预留、已执行激活和 replan 剩余额度，测试须证明重判不能重置已消耗预算。
8. 计划和决策计数随 checkpoint 保存，之后仍经现有持久化/授权/执行链路。重启不能重置协作重判次数；每任务初判一次、最多重判一次。

## 4. FIFO、取消与迟到结果

- 准备过程属于现有 Facade FIFO 内的规划阶段；不可直接从 port 修改 coordinator。
- M11 单次 attempt 超时不能代替整个准备阶段的总时限。为整个阶段配置总时限（建议默认 5000 ms），包括 loader 与 release runner；总时限到达后取消子操作并丢弃迟到结果。
- 单纯策略失败、超时或策略评估取消回退 Single；整个任务取消/应用 shutdown 不能回退后继续调用 Planner 或工具。
- 当前 cancelTask/shutdown 也排在 FIFO，不能等待准备阶段自行完成才发出取消信号。拟由 Facade 对当前任务的有效取消请求发出内部信号，只停止准备计算；业务状态迁移、回执与持久化仍由 FIFO 处理。无效 taskId/控制命令不得取消别的任务。
- 被任务控制请求中断的准备阶段退出后，不调用 Planner/Adapter，交由队列中的控制命令完成状态迁移。若控制命令未被接受，需要明确可继续的状态，不能遗留悬挂任务。
- 任意异步结果必须绑定 taskId、evaluation generation、输入摘要及 Registry 版本。取消、超时、Registry 漂移或新一代评估后，旧结果无效。

## 5. checkpoint 与恢复兼容

新增重判计数及准备状态时需要显式版本化，不在旧 checkpoint 1.1 上偷偷增加必填字段。实现前列明新 checkpoint 版本和旧版本读取策略。

旧记录没有策略准备阶段的证据，不能推断 learned 评估已通过。兼容迁移只允许保持既有 baseline；含旧 MULTI/缺失决策计数且无法证明重判上限的记录应明确拒绝或进入受控对账，不能默认计数为零后继续研究策略。

准备中的任务在恢复时不能自动启动真实 policy/network。T53 仅用 fake 验证取消失效、恢复绑定及重判上限；实际服务资源释放不在本轮冒充完成。

## 6. 影响范围与验证门

实现预计涉及 Runtime 的 ports/composition、coordinator、checkpoint validator、M11 适配器及测试；跨模块只修改受影响的 connector/storage 透传和对应定向测试。不得修改 UI、真实 Provider 配置、训练环境或生产发布状态。

最低验证：

- 默认关闭、缺产物、loader 失败、超时、评估取消、低置信度、NaN/Infinity、越界角色/模型和预算不足均按约定回退。
- 正向 fake 候选得到可校验计划；同任务最多一次重判，恢复后上限不重置。
- task cancel/shutdown 期间 Planner/Adapter 调用数保持零；迟到结果不能发布；错误任务的取消无影响。
- Registry/输入变化、重复 prepare、跨任务缓存串用均拒绝。
- checkpoint round-trip、旧版本兼容边界及组合端口透传。
- 受影响 Hypium 套件与 Runtime Release HAR；不运行真实 Provider、训练、签名或设备批次。

当前本地 clone 未发现 `oh_modules`，原测试脚本还固定使用另一台机器的 `D:\DevEco` 路径。实施时需先定位本机已有工具与可复用依赖；不得把缺依赖、未运行的构建写成通过，不新增依赖版本。

## 7. 不采用的方案

- 把现有 selectPlan 直接改成 Promise：会破坏所有同步调用方。
- 在同步接口中启动未等待的异步调用：产生竞态，无法保证预算、取消和计划一致性。
- 仅离线预选一个固定策略并宣称完成按任务路由：不能证明 T53 的任务绑定与逐任务回退。

## 8. 已批准范围

项目所有者已批准“可选异步准备端口 + 保留同步选择接口”、composition/checkpoint 版本化、FIFO 内部取消接线及受影响模块透传。

批准不包含训练、真实模型调用、下载研究模型、生产 active 发布、Git 提交/推送或设备操作。T53 实现和验证通过前仍保持未完成。

## 9. 实现落点

实际 prepare 返回 Promise<void>，经过验证的结果保留在同一 adapter 实例的任务/输入/Registry/generation 绑定缓存；通过同一实例同时绑定 preparation 与 selector，不新增第二个任务入口。composition 2.6、checkpoint 1.2；原 usage.agentActivations 保守累计完整计划占用，不因失败退款。旧 Single 迁移为 baselineOnly；旧 MULTI 拒绝，pending 恢复返回受控对账原因。详见 [T53 接入与验收](https://github.com/AlterGo-xzy/Harmony_agent/blob/f1771764f129193725a8bccb5da2be6c3604e998/docs/architecture/T53-%E5%8D%8F%E4%BD%9C%E7%AD%96%E7%95%A5%E6%8E%A5%E5%85%A5%E4%B8%8E%E9%AA%8C%E6%94%B6.md)。
